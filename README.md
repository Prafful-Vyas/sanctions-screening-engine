# Sanctions / Watchlist Name Screening Engine

Batch screening of customer records against a sanctions watchlist (OFAC SDN / UK HMT
style), built the way a bank's financial-crime platform has to work: **explainable**
scores, high recall, and a defensible way to cut the false-positive alert volume that
makes screening expensive.

```
customers.csv ──► normalise ──► phonetic blocking ──► pairwise scoring ──► rule threshold ──► alerts
watchlist.csv ──► normalise ──► Soundex index    │                      (name ≥ 0.88)      │
                                                 └── DOB / nationality / type signals      ▼
                                                                         ML prioritisation (logistic
                                                                         regression, JSON coefficients)
                                                                                   │
                                            OPEN alerts ◄──────────────────────────┤
                                            AUTO_CLOSED (p < cut-off) ◄────────────┘
                                                      │
                                     Oracle (prod) / SQLite (tests): screening_run, screening_alert
```

## What it does

| Stage | Module | Detail |
|---|---|---|
| Normalisation | `screening/normalize.py` | Diacritic folding, honorific and legal-suffix removal (`L.L.C.` = `LLC` = dropped for entities only), particle joining (`Al Rashid` = `Al-Rashid` = `Alrashid`), transliteration variants (`Mohammed/Mohamed/Muhammad`). |
| Candidate generation | `screening/watchlist.py` | Soundex blocking index over every primary name and alias, so each record is compared only against list names sharing a phonetic key. |
| Scoring | `screening/similarity.py`, `engine.py` | Jaro-Winkler implemented in-house (reference values tested), order-free one-to-one token alignment, token coverage (one shared token like "Muhammad" is not a match), and secondary DOB / nationality / party-type signals. Every field in an alert can be recomputed by hand. |
| Alert decision | `engine.py` | Name score ≥ threshold raises an alert. DOB and nationality adjust the score but never suppress a strong name match on their own. |
| Prioritisation | `screening/model.py` | Logistic regression over the match features. The auto-close cut-off is chosen on a held-out 30% so that ≥ 99% of true matches stay open. Coefficients are saved as JSON (no pickle), so the model can be reviewed and loaded safely. |
| Persistence | `screening/store.py`, `sql/` | Named-bind SQL that runs unchanged on python-oracledb and sqlite3. Oracle DDL uses interval partitioning by month so retention is a partition drop. |
| Batch ops | `scripts/screen_batch.sh` | Cron/Autosys wrapper: input validation, `flock` single-run lock, per-run logs, log retention, distinct exit codes for the scheduler. |

## Results (synthetic data, `scripts/gen_data.py --seed 42`)

1,500 list entries (80% individuals across Arabic, Russian, Chinese, Hispanic and
Persian naming conventions, 20% entities) and 20,000 customers: 2% planted true
matches perturbed with typos, transliteration, reordering, honorifics, diacritics,
dropped middle names and alias use, 3% namesakes (same name, different person), and
the rest background.

| Metric | Value |
|---|---|
| Rule-engine recall on planted matches (threshold 0.88) | **99.3%** (411 / 414) |
| Alerts raised | 5,787 (7.1% precision) |
| Model, held-out set: alerts auto-closed | **75.7%** |
| Model, held-out set: recall of true matches kept | **99.2%** |
| Model, held-out set: precision of remaining open alerts | 7.1% → **28.9%** |
| Throughput (single process, laptop) | ~350 records/s |

These numbers are from synthetic data generated by this repo. They show the method
works. They are not a claim about production performance on a real list.

## Run it

```bash
pip install -e .[dev]
python scripts/gen_data.py --out data
python -m screening evaluate --watchlist data/watchlist.csv --input data/customers.csv --labels data/labels.csv
python -m screening train    --watchlist data/watchlist.csv --input data/customers.csv --labels data/labels.csv --out data/alert_model.json
python -m screening screen   --watchlist data/watchlist.csv --input data/customers.csv --model data/alert_model.json --db data/screening.db
# or, as the scheduler would:
scripts/screen_batch.sh data/customers.csv
pytest
```

Oracle: `pip install -e .[oracle]`, apply `sql/oracle/001_schema.sql`, and pass a
`store.connect_oracle(...)` connection. The insert and update statements are the same ones the
SQLite tests exercise.

## What was verified

* `pytest`: 30 tests covering normalisation, Jaro-Winkler / Soundex reference values,
  perturbation detection, entity legal-form handling, namesake scoring, the SQLite
  store round trip, and model recall plus JSON round trip. Runs in CI (GitHub Actions).
* The results table above comes from real runs of the CLI on the generated data.
* **Not verified against a live Oracle instance.** The Oracle DDL and the oracledb code
  path have not been run. `screen_batch.sh` passes a syntax check (`bash -n`) and was
  not run under a real scheduler.
